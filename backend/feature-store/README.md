# feature-store

Transforms validated OHLCV market data into versioned, point-in-time-correct
engineered features. This is the AQROS Phase 2 slice of the eventual
Feature Store Service described in `docs/AI_QUANT_PLATFORM_BLUEPRINT.md`
§3.2 and `docs/claude_ROI.md` §11–12 — scoped to offline batch/incremental
computation of technical indicators over daily bars (no online/Redis
serving, no streaming, no ML consumption yet; those are later phases).

## Service boundary: how this reads market data

The Feature Store **never connects to the Market Data Service's database**.
It reads OHLCV bars exclusively through market-data's *published REST API*
(`GET /v1/instruments/{symbol}/bars`), via `adapters/market_data_client.py`.
This is a direct application of CLAUDE.md §7.9 ("NEVER let a service reach
into another service's database or internals") — the two services are
independently deployable, and market-data's schema can change without ever
breaking this one, as long as its API contract holds.

## Architecture (ports-and-adapters)

- `domain/` — pure business logic, no I/O:
  - `models.py` — `OHLCVBar` (local type, decoupled from market-data's own),
    `FeatureDefinition`, `FeatureValue`, `FeatureComputationRun`, `FeatureStatistics`.
  - `indicators.py` — pure pandas functions for every required indicator.
    Every function is **strictly causal** (trailing rolling windows,
    backward-only shifts, causal EWM) — no feature may see the future.
  - `feature_definitions.py` — the catalog: 18 registered features, each
    pairing an immutable `FeatureDefinition` with its compute function.
  - `validation.py` — rejects NaN/Inf values and any point-in-time violation.
  - `ports.py` — `MarketDataSource`, `FeatureDefinitionRepository`,
    `FeatureValueRepository`, `FeatureComputationRunRepository`.
  - `services.py` — `FeatureEngineeringService` (full/incremental pipeline
    runs) and `FeatureQueryService` (values, definitions, statistics).
- `adapters/` — concrete I/O:
  - `market_data_client.py` — `HttpMarketDataSource`, an httpx-based client
    against market-data's REST API (paginated, retried with backoff).
  - `db.py` / `orm.py` / `repository.py` — async SQLAlchemy 2.0 engine,
    ORM models, and Postgres-backed repository implementations.
- `api/` — FastAPI routes (`routes/features.py`, `routes/pipeline.py`),
  Pydantic schemas (`schemas.py`), and DI wiring (`deps.py`).
- `migrations/` — Alembic migrations (`feature_definitions`, `feature_values`,
  `feature_computation_runs` tables).

## Feature catalog

| Category | Features |
|---|---|
| Trend | `sma_20`, `ema_20` |
| Momentum | `rsi_14`, `macd_line`, `macd_signal`, `macd_histogram` |
| Volatility | `atr_14`, `bollinger_upper`, `bollinger_middle`, `bollinger_lower` |
| Volume | `obv`, `vwap_20` |
| Returns | `daily_return`, `log_return` |
| Rolling stats | `rolling_mean_20`, `rolling_std_20`, `rolling_min_20`, `rolling_max_20` |

Every feature is versioned (`name`, `version`) and immutable once registered
— changing a feature's computation logic means registering a new version in
`domain/feature_definitions.py`, never mutating an existing one in place
(CLAUDE.md §10).

## Point-in-time correctness

Every stored `FeatureValue` carries both `event_time` (the bar it describes)
and `knowledge_time` (when the feature was computed). The retrieval API
accepts an optional `as_of` query parameter that hard-filters to
`knowledge_time <= as_of` — a consumer reconstructing "what did we know on
date X" can never see a feature computed after X (docs/claude_ROI.md §17).

## Endpoints

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/v1/pipeline/compute` | Run the pipeline for a symbol (`mode: full \| incremental`) |
| `GET` | `/v1/pipeline/runs/{run_id}` | Fetch one computation run (audit record) |
| `GET` | `/v1/pipeline/runs` | List computation runs, optionally filtered by symbol |
| `GET` | `/v1/definitions` | List the feature catalog |
| `GET` | `/v1/definitions/{name}` | Fetch the latest version of one feature definition |
| `GET` | `/v1/instruments/{symbol}/features/{feature_name}` | Retrieve stored values (filterable by date range, `as_of`, paginated) |
| `GET` | `/v1/instruments/{symbol}/features/{feature_name}/statistics` | count/mean/std/min/max for a feature |
| `GET` | `/health`, `/health/live`, `/health/ready` | Health probes (readiness checks the DB and Market Data Service reachability) |
| `GET` | `/docs`, `/openapi.json` | OpenAPI docs (auto-generated by FastAPI) |

## Batch vs. incremental computation

- **`full`** always recomputes every feature over the entire available
  history for a symbol.
- **`incremental`** computes from a high-water mark (the latest already-
  computed `event_time` across every feature), minus a lookback buffer
  (`AQROS_FEATURE_LOOKBACK_BUFFER_DAYS`, default 90 days) so windowed
  indicators (e.g. a 26-bar MACD) have enough trailing history to compute
  correctly for newly-added bars. If any feature has never been computed for
  a symbol, incremental mode falls back to a full fetch.

Both modes upsert (never duplicate) on `(symbol, feature_name,
feature_version, event_time)`, so re-running a computation is always safe.

## Running locally

Via Docker Compose (recommended — brings up both this service's Postgres
*and* market-data + its Postgres):

```bash
docker compose up -d market-data-db market-data feature-store-db feature-store
docker exec -w /app/backend/feature-store <container> python -m alembic upgrade head
curl localhost:8003/health/ready
```

Directly (needs a reachable Postgres and a reachable Market Data Service):

```bash
uv run --directory backend/feature-store alembic upgrade head
uv run python -m aqros_feature_store.main   # listens on port 8003
```

## Configuration (env vars, prefix `AQROS_`)

| Variable | Default | Purpose |
|---|---|---|
| `AQROS_DATABASE_URL` | `postgresql+asyncpg://aqros:aqros@localhost:5433/aqros_feature_store` | Async SQLAlchemy DSN (own database) |
| `AQROS_MARKET_DATA_BASE_URL` | `http://localhost:8002` | Market Data Service REST API base URL |
| `AQROS_MARKET_DATA_REQUEST_TIMEOUT_SECONDS` | `30.0` | Per-request timeout to market-data |
| `AQROS_MARKET_DATA_MAX_RETRIES` | `3` | Retry attempts on market-data failure |
| `AQROS_MARKET_DATA_PAGE_SIZE` | `1000` | Pagination page size when fetching bars |
| `AQROS_FEATURE_LOOKBACK_BUFFER_DAYS` | `90` | Trailing buffer for incremental recomputation |

See root `.env.example` for the full list shared with other services.

## Tests

- `tests/unit/` — pure domain logic: indicators (hand-verified against
  independently computed values, plus a causality/no-lookahead test),
  validation, the feature catalog, and pipeline orchestration against fakes
  for every port. No I/O, run on every commit.
- `tests/integration/` — real Postgres via testcontainers (repository
  behavior including the `as_of` PIT filter, the full API through
  `httpx.AsyncClient` with a faked `MarketDataSource`, and an Alembic
  `upgrade head` schema check). Requires Docker; marked `integration`.

```bash
uv run pytest backend/feature-store                      # unit + integration
uv run pytest backend/feature-store -m "not integration"  # unit only, no Docker
```
